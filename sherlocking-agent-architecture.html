Deep Research Agent Kernel

Sherlocking 是怎么搭建这个 Agent 的

这是一份对 sherlocking 项目代码的架构拆解：它如何用 LangChain / LangGraph 把一个「深度研究 Agent」拆成可插拔、可独立测试的层次——薄壳 Leader + 编译图 + 中间件横切 + 分层记忆 + 多智能体 + 沙箱隔离。

Overview

一句话总览

Sherlocking 的核心是一个编译好的 LangGraph 智能体图（create_agent 生成）， 外层包一个几乎不做事的 LeaderAgent 薄壳。真正的研究智能（多轮决策、工具调用、退出逻辑） 全部藏在图内部，通过 20+ 个中间件（AgentMiddleware）横切到每个生命周期钩子上。

一句话总结设计思路：「app → agents」单向依赖，中间件是一等公民—— 记忆召回、技能注入、沙箱生命周期、巩固、工具配对、求助、上下文治理，全都是可插拔的横切关注点， 而不是硬编码进 agent 循环里。

Philosophy

设计哲学：中间件优先，模块解耦

Sherlocking 不是「堆功能清单」，而是建立一套干净、解耦、可评测的地基。四条主线贯穿始终：

1. 中间件是一等公民

记忆、技能、沙箱、工具路由、上下文治理……全部是可插拔的横切中间件，通过 before/after_agent、before/after_model、wrap_tool_call 钩子切入，而不是写死在循环里。关掉某个功能 = 不挂对应中间件。

2. 严格单向依赖

app → agents 依赖方向固定。App 层只做装配（bootstrap），不掺和智能逻辑；agents 层各模块彼此独立、独立测试。

3. 「工具里无 LLM」

记忆的原子操作（编码/检索/关联/巩固）是纯数据操作；LLM 编排放在中间件/worker 层。技能是「提示级注入」，不是可执行函数。

4. 真实值优先于静态配置

上下文窗口大小穿透 FallbackChatModel 拿到真实 provider 的 context window，而不是硬编码阈值；模型名也取路由链实际 provider 名。

Bootstrap

启动装配流程（bootstrap_runtime）

入口 sherlocking.backend.app.cli.main:main 启动后，bootstrap_runtime() 按固定顺序把整个 agent 拼装出来。这是理解「它是怎么搭起来」的主线。

load_config 建 thread 目录 + RunJournal ModelRouter 建模型 内置工具 ddg/read_snapshot MCP 工具加载 沙箱 provider + 工具 技能系统 + 进化 + 评测 多智能体 setup 记忆 provider + worker CapabilityRegistry make_lead_agent → create_agent

每一步在做什么

步骤关键代码说明
1. 配置load_config(expert_mode, cli_overrides)读 .env + YAML profile（general/fast/expert），产出不可变 AppConfig。
2. 日志骨架RunJournal(events_path=thread-events.jsonl)每个 thread 一个目录，结构化事件流（JSONL）贯穿全程。
3. 模型ModelRouter().build_model("researcher"|"reporter")按角色路由链构造 FallbackChatModel，DeepSeek 兜底；--provider 则单 provider。
4. 内置工具get_available_tools(groups=["core"])ddg_search、read_snapshot 始终注册——MCP 关闭时的唯一搜索来源。
5. MCPbuild_mcp_manager() → 审计中间件仅当 npx 可用；core 工具启动加载，deferred 按需加载，工具元数据喂给外化层阈值。
6. 沙箱_load_sandbox_provider（反射加载）+ make_sandbox_tools配置指定 provider 就加载，产出 8 类沙箱工具 + ArtifactServer。
7. 技能build_skill_manager() → 注入/指标中间件启用则加载 36 个内置技能 + 自进化（EvolutionManager）+ 评测（EvalLayer）。
8. 多智能体setup_multiagent(agent_factory=_subagent_factory)注入闭包工厂，构建 leaf-role 子 agent（不能再 spawn）。
9. 记忆set_memory_config + start_memory_worker同步全局单例配置，启动后台 daemon 线程做 L5 抽取/巩固。
10. 注册表CapabilityRegistry(models, tools, ...)统一存放 researcher/reporter 模型、工具、reporter、artifact_store、沙箱、技能、专家、记忆。
11. 编译图make_lead_agent(...)把模型 + 工具 + 中间件列表 + system prompt + checkpointer 喂给 create_agent。
CapabilityRegistry 是装配的「容器」——它要求 直接存实例（BaseChatModel / BaseTool）， 而不是存字符串名。各层通过 get_model() / get_tool() / get_skill_store() 等方法取用，缺失抛 CapabilityMissingError。
ReAct Kernel

ReAct 内核：薄壳 + 编译图

LeaderAgent 是「薄壳」

LeaderAgent 只是个 dataclass，持有 graph 和 capability_registry。 它的 run() 只做四件事：构造初始状态、拼 configurable、调 graph.ainvoke()、按模式取报告。 

@dataclass
class LeaderAgent:
    """Thin shell: invokes compiled graph + collects report."""
    graph: Any
    capability_registry: CapabilityRegistry

    def run(self, question, run_context):
        initial = create_initial_thread_state(question)
        config = {
            "configurable": { "thread_id": ..., "journal": ...,
                            "model": _resolve_actual_model_name(...) },
            "recursion_limit": max_loop_steps * graph_node_multiplier,
        }
        final_state = asyncio.run(self.graph.ainvoke(
            {"messages": [HumanMessage(content=question)]}, config=config))
        # expert 模式取 final_report；default 模式取最后一条 AIMessage
ReAct 的「多轮决策 / 工具调用 / 退出逻辑」全部在图内部，靠 create_agent + 中间件完成。 recursion_limit 从配置推导（max_loop_steps × graph_node_multiplier）， 不再硬编码——长任务有足够图节点预算，安全网是 StallDetectionMiddleware。
常见误解澄清：LangGraph 到底用没用？ 全项目代码里没有任何手写 StateGraph / add_node / add_edge—— 图是 LangChain 1.x 的高层 API create_agent(model, tools, middleware, ...) 生成的。 但「没有手写」不等于「没用 LangGraph」：create_agent 返回的对象本身就是 LangGraph 编译图（测试里直接断言 graph.__class__.__name__ == "CompiledStateGraph"）， 而且中间件体系与 LangGraph 原生类型深度绑定——钩子签名里的 Runtime、 返回的 Command、@hook_config(can_jump_to=["model"]) 跳节点、 InMemorySaver checkpointer、get_stream_writer() 流事件、 graph.ainvoke / astream，全部是 LangGraph 的 API（共 53 处 import）。 准确说法是：LangGraph 是执行引擎，create_agent 只是把 model ⇄ tools 的 ReAct 骨架封装成图；Sherlocking 把几乎所有业务逻辑写在中间件层，而中间件通过 LangGraph 的 Command / Runtime 机制横切这张图。

make_lead_agent —— 图的装配工厂

工厂函数把「模型 + 工具 + 中间件 + system prompt + 状态 schema + 检查点」一次性喂给 LangChain 的 create_agent：

return LeaderAgent(
    graph=create_agent(
        model=model,                      # registry.get_model("researcher")
        tools=tools or None,            # core 或 core+deferred（expert）
        middleware=_build_middlewares(...), # 20+ 中间件列表
        system_prompt=apply_prompt_template(...),
        state_schema=ThreadState,          # 扩展 AgentState 的状态 schema
        checkpointer=get_checkpointer(),    # 单例，thread 跨轮/跨模式保留 state
    ),
    capability_registry=registry,
)

两个模式由 expert_mode 参数化区分：

维度default（轻量）expert（深度研究）
工具组仅 corecore + deferred
Todo 中间件不强制完成强制完成
ReflectionLightReflectionStrategy（不 jump）SufficiencyStrategy（充分性 jump）
报告不自动合成，靠 /reportReportMiddleware after_agent 自动合成
Middleware

中间件系统（核心）

这是整个项目最关键的抽象。每个中间件继承 LangChain 的 AgentMiddleware， 重写需要的生命周期钩子；返回 Command 可写状态 / 注入消息 / 跳转节点。 钩子共有三组：

before / after_agent

一次 run 的开头与结尾。沙箱在 after_agent 释放、预算在 before_agent 初始化。

before / after_model

每次调 LLM 前后。记忆召回注入、技能注入、失败摘要、上下文治理全在这里。

wrap_model_call / wrap_tool_call

包裹模型调用与工具调用。工具账本、沙箱 acquire、多智能体打点在这里。

关键机制：@hook_config(can_jump_to=["model"]) 允许中间件把流程跳回 model 节点； 返回 Command(update={...}) 可持久化写状态。这让「反思后重试」「预算耗尽强制收尾」成为可能。

中间件挂载顺序（_build_middlewares）

顺序至关重要——它是「洋葱模型」的层次：

TaggedContext MessageNormalizer StrategyMiddleware(治理) SystemContext SkillInjection SkillMetrics SkillActivation Title RunJournal McpAudit Sandbox Memory(L4) MemoryConsolidation(L5) HelpRequest DanglingToolCall ToolCall Orchestration Evidence StallDetection Todo Reflection Report

几个代表性中间件的职责

中间件钩子职责
ToolCallMiddlewarewrap_tool_call / before_model工具调用账本：成败都记 errors，按异常类型分类，per-tool 连续失败重试预算，硬预算兜底；失败摘要延迟到 before_model 注入（避免破坏工具配对）。
SandboxMiddlewareabefore_model / awrap_tool_call沙箱懒获取：首次调沙箱工具才 acquire；abefore_model 从 state["sandbox"] 恢复 ContextVar，子 agent 复用父沙箱；present_files 后登记产物。
MemoryMiddlewareabefore_model记忆召回：每调用注入一条 HumanMessage(hide_from_ui=True)（保护 prompt cache），set_turn_id 上下文变量标记轮次。
StrategyMiddleware全部 6 钩子上下文治理适配器：把治理策略 bundle 的 6 hook 路由到 AgentMiddleware 钩子。
OrchestrationMiddlewarewrap_tool_call拦截 delegate_to_*，打四计数器 + 写编排状态，失败转 error ToolMessage。
ReflectionMiddlewareafter_model反思循环：expert 用充分性策略（不足则 jump 回 model 继续），default 用轻量策略。
一个体现「工具无 LLM、编排在中间件」的细节：MemoryWorker 在中间件层调 LLM 抽取记忆， 而 DefaultMemoryManager 只接受外部传入的 content 做纯数据操作——职责边界非常清晰。
State

状态管理：ThreadState + Reducer

ThreadState 继承 LangChain 的 AgentState（已含 messages 的 add_messages reducer）， 再扩展出研究过程所需的全部字段。每个字段带 Annotated reducer 驱动图内状态合并： 

class ThreadState(AgentState):
    user_input: NotRequired[str]
    intent: NotRequired[Any]
    research_question: NotRequired[str]
    observations: Annotated[list, merge_observations]
    sources:      Annotated[list, merge_sources]
    citations:    Annotated[list, merge_citations]
    artifacts:    Annotated[list, merge_artifacts]
    final_report: Annotated[str | None, merge_final_report]
    errors:       Annotated[list, merge_errors]      # 也是工具调用账本
    todos:        Annotated[list | None, merge_todos]
    governance:   Annotated[GovernanceState | None, merge_governance]
    sandbox:      Annotated[dict | None, merge_sandbox]
    orchestration: Annotated[OrchestrationState | None, merge_orchestration]
    recalled_memories: Annotated[list | None, merge_memory_recalled]
    ...
checkpointer 是跨轮记忆的关键：get_checkpointer() 返回单例， 同一个 thread_id 的多轮对话、甚至 /expert、/model、/mcp reload 热切换重建 agent 后，历史 state 仍然连续（checkpointer 状态跨重建保留）。
Context Governance

上下文治理：把 token 预算当一等公民

长研究会话会撞上下文窗口。治理层通过一个「策略 bundle」动态外化 / 压缩历史消息。 核心是 GovernanceStrategy 协议（6 个 hook），StrategyMiddleware 把 bundle 接到中间件系统上。

契约：GovernanceContext → GovernanceResult

@dataclass(frozen=True)
class GovernanceResult:
    state_patch: dict | None = None      # 写 ThreadState（持久）
    request_override: Any | None = None  # 替换请求（request 级，不持久）
    messages_patch: list | None = None   # RemoveMessage / 替换消息
    metrics: list = ...                 # 策略级指标
    jump_to: str | None = None          # 跳转目标节点

DefaultStrategy 的分段预算（P0–P5）

每次 after_model 用 token 计数器算 fraction（占用比例），按阈值触发不同动作：

阶段阈值动作
P1 externalize40%把历史消息外化到文件，替换为预览引用（间隔抑制 +10% 防抖）。
P2 thinking50%标记推理内容（reasoning_content）。
P3 observations60%观察 top-N（渲染层筛）。
P4 summarize80%压缩：先快照，再 LLM 摘要，保留最近 6 条。
P5 stop toolcall90%剥掉最后 AIMessage 的 tool_calls + 注入「收尾」提示 + jump_to="model"。
hard_stop99%强制收尾，禁止再调工具。
突破点：窗口大小通过 resolve_window_size(model) 穿透 FallbackChatModel 拿到真实 provider 的 context window，而不是硬编码阈值——因此 P5 熔断阈值在切换 provider 后依然准确。

治理层还自带防御性配对校验：送 LLM 前确保每个 AIMessage(tool_calls) 都有配对的 ToolMessage，缺失则补占位——避免 API 400。

Memory

五层长期记忆系统

认知科学启发的五层记忆，每层独立可测。核心原则贯穿：工具里无 LLM，纯数据操作。

层角色关键实现
L1 Schema + Protocol数据契约MemoryTrace 冻结 dataclass（15 字段）+ MemoryType 枚举（episodic/semantic/procedural）+ 5 原子操作。
L2 Default Strategies衰减/遗忘艾宾浩斯衰减公式 strength = base×(1-decay)^hours + log(1+access)×0.1 + importance×0.05；复合遗忘（TTL + 强度阈值）；懒衰减——检索时才算强度，无后台任务。
L3 Store + Retriever持久化/检索MarkdownFileStore（单 traces.md 真相源 + <!-- trace: {id} --> 分隔 + YAML frontmatter）；HybridRetriever（纯 BM25，无向量/图依赖）。
L4 Middleware + Bootstrap注入/生命周期MemoryMiddleware.abefore_model 每调用注入 HumanMessage（保护缓存）+ set_turn_id ContextVar。
L5 Auto-Consolidation后台巩固MemoryConsolidationMiddleware.aafter_model 非阻塞提交 + MemoryWorker（daemon 线程 + 队列 + LLM 注入），LLM 抽取 episodic → 满 N 条 → LLM 生成合并内容 → manager.consolidate。

检索与巩固的机制细节

HybridRetriever（纯 BM25）

  • 复合分数：score = similarity×0.7 + strength×0.3。
  • 检索强化写回：命中后 store.update 增强 strength。
  • 遗忘过滤：metadata.forgotten=True 直接排除。
  • 增量索引：store 装饰器触发 on_trace_* 维护倒排索引。

DefaultMemoryManager（四操作）

  • encode：id = SHA256(content+type)[:16]，同内容同类型幂等。
  • associate：双向关联，超上限 LRU 淘汰最弱。
  • consolidate：最多合并 10 条，旧 trace 标记 forgotten 不删除。
  • reconsolidate：保留原强度 + last_accessed=now。
  • 全程 append operation_log（可追溯），actor 取自 ContextVar。
保护 prompt cache：记忆注入用每调用一条的 HumanMessage（不是塞进 system prompt）， 不破坏 LLM 的 prompt 缓存前缀；recalled_memories 只存索引（id+score+strength），不存全量内容。
Tools

工具生态：MCP + 内置 + 沙箱

工具来源有三类，统一进 CapabilityRegistry.tools，由 get_available_tools(groups=...) 按组筛选。

内置工具

ddg_search（DuckDuckGo）、read_snapshot、skill_search、ask_help。MCP 关闭时是唯一搜索来源。

MCP 工具

三传输 stdio / sse / http；core 启动加载、deferred 按需；.sherlocking/mcp_servers.yaml 配置；带安全 guards（凭据清洗、描述扫描、env 过滤）。

沙箱工具

8 个（bash / write_file / str_replace / present_files 等），由 make_sandbox_tools 生成，路由到 Local/Docker provider。

还支持工具等价回退链：例如 web_search → MCP server → 内置 ddg，保证搜索韧性。工具元数据进一步驱动外化层的阈值。

Sandbox

沙箱隔离与路径强制

双 provider：Local（宿主进程，开发）与 Docker（容器隔离，生产）。沙箱中间件做懒获取生命周期管理。

生命周期（SandboxMiddleware）

  • 懒获取：首次调沙箱工具才 acquire(thread_id)，无 before_agent。
  • 共享线程沙箱：abefore_model 从 state["sandbox"] 恢复 ContextVar，子 agent 复用父 sandbox_id 而不重复获取。
  • after_agent release：释放但不销毁（Local 是 no-op）。

Docker 模式的突破

  • DockerPathTranslator：/mnt/sherlocking/user-data/<x> → Windows 宿主真实路径。
  • DockerPathGuard：写路径白名单，强制 agent 写入挂载区（否则 --rm 丢容器内临时文件）。
  • 预热池 + 空闲自动销毁（10min）+ 跨进程锁 + WSL2 执行器。
present_files 的产物链：从挂载区复制到固定 .sherlocking/outputs/，再注册到 ArtifactServer 供 HTTP 下载——用户永远知道产出物在哪。
Multi-Agent

多智能体编排

两种委托方式，都通过 delegate_to_* 工具暴露给 leader 的 LLM 决策（soft routing，编排决策是 LLM 做的）。

🤖 Specialist Delegation（外部专家）

delegate_to_specialist 路由到外部 CLI（pi / codex / claude），经 MCP SpecialistMcpServer 暴露 8 个沙箱工具。每个专家独立进程、独立 LLM，但通过 --sandbox-url 共享同一 Docker 沙箱。

🧬 Subagent（自我复制）

delegate_to_subagent 创建 Sherlocking 自拷贝：隔离上下文（不继承父消息历史）但共享线程沙箱。由 SubagentRuntime 调 agent_factory 造 leaf-role 子 agent。

递归防护（INVARIANT）：_subagent_factory 闭包构造 leaf agent 时传 specialist_tools=None + orchestration_middleware=None—— 子 agent 看不到 delegate_to_* 工具，无法再 spawn，实现 max_spawn_depth=1 的 leaf-only MVP。

此外还有 L2 进化层（MetricMonitor 触发 → IVEFocuser 诊断 → LLMMutator 变异 → ScoreDeltaGate 门控 → GitRatchet 回滚）与 L3 评测层（执行判断 + 四维任务质量 + 响应契约检查），让专家能力数据驱动自进化。

Skill

三层技能架构

技能是研究流程知识包——提示级注入，不是可执行函数。「如何验证来源」是技能，「执行搜索」是工具。

Layer 1 基础

SQLite 存储 + 版本 DAG + 质量过滤的 LLM 混合选择 + 注入中间件 + 四计数器（选择/应用/完成/回退）。

Layer 2 进化

有效率低于阈值时自动进化：IVEFocuser 诊断、LLMMutator 变异、ScoreDeltaGate 门控、GitRatchet 回滚。

Layer 3 评测

执行判断 + 任务质量评分（四维加权）+ 响应契约检查；RuntimeTracker 把退化信号回喂 L2。

共 36 个内置技能、5 大类（core / research / software-development / creative / productivity）；core 自动加载，其余经 /skill search 发现。

Model

多 LLM 路由与降级

ModelRouter 按角色（researcher / reporter）构造路由链。 每个角色得到一条 FallbackChatModel：遇到瞬时故障（限流/超时/5xx）自动降级到下一 provider，DeepSeek 永远在链尾兜底。 

class ModelRouter:
    def build_model(self, role):
        chain = route_chain_for(role, self._providers)
        models = [build_chat_model(p) for p in chain]
        return FallbackChatModel(models=models, provider_names=[p.provider ...])

    def build_single(self, provider, model):   # CLI --provider 强制单 provider
        cfg = select_provider_config(provider=provider, model=model)
        return build_chat_model(cfg)

上下文中 _resolve_actual_model_name 会取 FallbackChatModel.provider_names——反映真实路由链，而非静态配置名（配置可能是 fake-researcher）。
